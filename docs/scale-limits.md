# 構成規模と描画規模の分離

2026-10-16。以下は合成データでの初期評価です。特定の機器数だけで性能や図の読みやすさは決まりません。多数のtrunk VLAN、共有関係、ラベル長、ケーブル経路も負荷に影響します。

## 採用する上限

| 対象 | 上限 | 目的 |
|---|---:|---|
| 構成全体のYAML（UTF-8） | 2 MiB | 入力・転送・解析の負荷を制限 |
| 構成全体の機器 | 256台 | 複数拠点を含む台帳を扱う |
| 構成全体の要素 | 10,000件 | ポート／IF／対応などを含めて制限 |
| 1回の描画の機器 | 24台 | 機器枠と配線の増大を抑える |
| 1回の描画のポート／IF行 | 200行 | ポート密度の高い機器を制限 |
| 1回の描画の接続／所属 | 400件 | trunkのVLAN所属なども個別に数える |
| 1回の描画の構成要素 | 500件 | レコード数に対する描画予算 |
| 1回の描画のVLAN／ブリッジ／サブネット | 80件 | 共有ネットワークの数を制限 |
| 出力SVG | 4 MiB | DOM・転送量の最終上限 |
| HTTP本文 | 8 MiB | JSONとしての転送量を制限 |
| 描画APIの同時処理 | 2件 | 同時処理でのメモリー増大を抑える |

保持はブラウザー内のエディターの構成全体を意味し、永続保存ではありません。全要素は機器、L1ポート・リンク・接続、L2 VLAN・IF・ブリッジ、L3サブネット・IF・経路、層間対応のレコードの合計です。描画側では表示中のレイヤーだけを数えます。所属リストは保持側のレコード数には含めず、描画側の接続数で数えます。追加のl1.connectionsも構成要素と接続件数に含み、ポート／無線IF未確認や相手未確認の専用表示も描画行数に数えます。YAMLノード数200,000・入れ子48段、各リストの既存上限、重複キー／エイリアスの拒否も適用します。

## 絞り込みの意味

拠点（location.site）、機器群（groups）、機器、層間対応の連結成分をANDで組み合わせます。層間対応はbindingsだけを双方向に追跡します。下位ポートを共有する別VLANの枝も含み、通信可能性を示すものではありません。

範囲外の機器を同じVLAN／サブネットから補完して表示することはありません。境界ケーブルは部分的な線を描かず、一覧と省略数で明示します。上限を超えると構成は検証済みのまま絞り込みを促し、先頭の一部を黙って表示することはありません。表示範囲外の参照も含めた全構成の検証が先に行われます。YAML保存は常に全構成、SVG保存は選択範囲です。

## 測定方法

Debian上のPython 3.12コンテナー。Webと負荷試験はそれぞれ1 CPU・512 MiB。PyYAMLのCローダーを用い、事前イベント走査でエイリアス・ノード数・深さを制限します。重複キーの拒否と行番号付きエラーは維持します。

bench_scale.pyを使い、15条件を各3回、新しいプロセスで測定します。時間はYAMLの検証・射影・SVG生成の合計で、プロセス起動とHTTP転送は含みません。個別プロセスのメモリーは/proc/self/statusのVmHWM、コンテナー全体はcgroup memory.peakです。全体ピークには試験データ生成側も含みます。並列2件のwall時間は子プロセス起動も含みます。

Chromium試験は実際のWeb APIを呼び、応答のJSON処理、SVGのDOM挿入・レイアウト・2回のアニメーションフレームまでを測定します。各条件3回です。画面外の描画はブラウザーが省略し得るため、画面全体の描画完了時間を保証する測定ではありません。エディターの500 ms待機・編集コストは含みません。編集・絞り込み・境界表示・保存・モバイル操作は別のブラウザー操作テストでも確認します。

大きい構成の単独APIにも最大2.25秒の変動があります。中央値だけで一定の応答時間を保証しません。

## 再実行

```sh
docker compose --profile qa run --rm benchmark
docker compose --profile qa build e2e
docker compose --profile qa run --rm e2e npm test -- --grep 'browser load timings'
```

詳細JSONはartifacts/scale-benchmark.jsonとartifacts/browser/scope-browser-benchmark.jsonに出力します。実機の構成情報は使いません。

## 判断と今後の見直し

保持量と描画量は独立に扱います。機器数だけを引き上げると、多数ポートやtrunkで描画負荷が急増するため、行・所属・ネットワーク数も制限します。保持側の上限は複数拠点を扱える範囲へ広げ、描画側の機器数は24台を維持します。小さい機器群や対応関係へ絞る運用を前提とします。

今回の合成データでの測定だけでは、複雑な配線、最長ラベルを多用した構成、多数利用者の長時間連続操作までの性能は保証できません。実際の構成を匿名化した追加ケースと継続負荷の結果に基づいて再評価してください。これは負荷と読みやすさを考慮した運用上限であり、ネットワークモデルが表現できる台数の理論限界ではありません。
